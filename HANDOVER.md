# Project Handover Document for Claude Code (and Human Teams)

Welcome to the `ha_xiaomi_home` project! This repository has undergone a massive modernization and architectural optimization in May 2026 (Version 20260527r7). 

Whether you are a human maintainer or an AI Agent (like Claude Code) taking over this project, **you must read this document first** to understand the architectural decisions, the performance optimizations, and the strict boundaries we have established.

## 📚 Essential Reading (Artifacts)
We have preserved our architectural research and decision-making history in the `docs/ai_architecture/` directory. AI Agents should index and read these files to understand the "Why" behind the code:
1. `docs/ai_architecture/xiaomi_miot_architectural_comparison.md`: Why we abandoned the Node.js wrapper for a native Python transpilation layer.
2. `docs/ai_architecture/miio_python_native_analysis.md`: The technical analysis of implementing zero-delay MIIO local control.
3. `docs/ai_architecture/miio_integration_analysis.md`: Analysis of how MIIO local control integrates with the existing Home Assistant ecosystem.

## 🚀 Key Architectural Upgrades (What you inherited)

### 1. Native Python MIIO Local Control (Zero-Delay)
We bypassed the legacy Node.js translation layer for 19 core devices (Yeelight lamps and Smartmi/Dmaker fans). These devices are now handled natively via the MIIO protocol, resulting in **zero-delay local execution** without cloud polling. 
**Rule**: Do NOT expand this whitelist arbitrarily. The zero-technical-debt promise relies on restricting this to highly stable, standard models.

### 2. $O(1)$ Data Structure Optimization
All major entity platforms (`climate.py`, `vacuum.py`, `cover.py`, `water_heater.py`, `select.py`, `humidifier.py`) have been heavily optimized:
- **No $O(N)$ scanning in runtime**: We replaced linear array scans with pre-computed $O(1)$ dictionary lookups (e.g., `_mode_reverse_map`, `_fan_level_reverse_map`).
- **List Comprehensions**: Deeply nested component loops in entity initialization (`async_setup_entry`) were flattened using Python List Comprehensions for faster boot times.

### 3. Bulletproof Entity ID Migration
The `async_migrate_unique_ids` script in `custom_components/xiaomi_home/__init__.py` handles the seamless migration of legacy entity IDs (stripping `xiaomi_home.` prefixes and handling `_control_path` / `_ip_address` isolation).
- **Self-Healing**: If HA generates a duplicate `_2` entity due to a dirty registry, this script automatically detects the collision, deletes the `_2` entity, and correctly binds the legacy entity.

## 🚫 STRICT RED LINES (DO NOT CROSS)
To prevent the codebase from regressing into a buggy, laggy state, observe these strict rules when adding features or fixing bugs:

1. **Do NOT blindly clamp sensor values**: In `sensor.py`, if a device reports a value outside its `value_range` (e.g., `temp < min_temp`), you MUST return `None` (Unavailable). Do NOT clamp it to `min_temp` or `max_temp`. Clamping destroys historical graph scaling and masks critical hardware failures.
2. **Do NOT remove the Mutex flags in Fan/Light devices**: We introduced `_is_turning_on` in `fan.py` to prevent race conditions during startup. Xiaomi devices will lag or crash if bombarded with overlapping `on=True` commands. Preserve concurrency safety.
3. **Do NOT merge `mode` and `brightness` into separate entities for Lights**: We unified them into `_effect_map` in `light.py`. Separating them causes mutual state overwrites when HA sends both commands simultaneously.
4. **Do NOT revert to $O(N)$ array searches**: Always use dictionary lookups (`_reverse_map.get(value)`) when converting between HA states and MIoT-Spec numerical values.
5. **Preserve `slugify_description=True`**: When generating unique IDs for services (like `Indicator Light`), ensure they are slugified (`indicator_light`) so they flawlessly match legacy Home Assistant registry entries.

## October 2026 Update (v0.5.1 to v0.5.14)

Maintenance of the fork was handed over to Claude Code on 2026-10-16. Decisions and conventions since then:

### Decisions
- **English only**: `INTEGRATION_LANGUAGES` contains only `en`; the Chinese translation and i18n files are gone and `bool_trans.yaml` / `multi_lang.json` keep English only. Config entries created with another language are migrated to English in `async_setup_entry` (entity IDs are kept). Do not re-add languages without updating `test/check_rule_format.py::test_miot_lang_integrity`.
- **Upstream PRs**: open upstream pull requests are ported once reviewed here, with the author kept and credited in the changelog and release notes. Upstream has no release after v0.5.0 (2026-09-28); its open fixes up to #1838 are in v0.5.3 and v0.5.4, and #1842 to #1844 are in v0.5.6. Last checked on 2026-11-11: nothing newer than #1852, and still no commit after v0.5.0. When the fork's code has diverged, the change is rewritten onto the fork with the PR author as commit author and the source PR named in the body. Reviewed and not ported: #1809 and #1841 (the owner declined them), #1840 (not needed: the fork never resubscribes an unchanged subscription source, and `MipsLocalClient` replays its subscriptions on reconnect), #1824 (another language), #1811 and #1813 (large new features), #1848 (the owner declined it: it adds every newly discovered cloud device to the device cache, which bypasses the home selection and device filters; new devices are meant to reach the cache through the device-list-changed notification and Options > Update device list), #1852 (not needed: the fork already serves the native temperature API for climate and water heater on 2026.11 and the old names on older cores; on 2026.11.0 its entities log no deprecation warning). Do not propose these again unless something changes.
- **Entity init loops stay**: the `for prop in entity_data.props` dispatch loops in cover, humidifier, media_player, vacuum, water_heater and device_tracker run once per entity. Replacing them with `get_prop()` would change last-match to first-match for duplicate property names, so they are kept on purpose.
- **Supported cores**: `hacs.json` declares Home Assistant 2026.11.0+ since v0.5.14 (2026.5.0+ up to v0.5.13); the owner agreed to raise it on 2026-11-11 so that `async_setup_entry`, `async_unload_entry` and `async_remove_entry` can return None, which older cores reject. The feature detection for older cores (`async_get_device_by_identifier`, the `native_*` temperature properties via `_NATIVE_TEMP_API`) is now dead code and can be removed. APIs introduced after 2026.11.0 are still used through feature detection with a fallback, never unconditionally.
- **License wording**: `LICENSE.md` is Xiaomi's own license, which allows use, modification and distribution only for non-commercial use with Home Assistant. Never describe the project as Apache 2.0 or open source (the README did until v0.5.5). Any change to the license or its description needs the owner's confirmation.
- **Home Assistant 2026.11**: checked against 2026.11.0b2 on 2026-10-31 (developer blog since August, release notes, b2 changes). Nothing breaks; v0.5.7 adds the two optional items: in-place entity ID renames and the Marketplace category. The 2026.11 Marketplace replaces HACS and migrates existing HACS installs, but it can only update a repository that has a `hacs.json`, so keep that file. The 2026.11.0 release (2026-11-04) was verified on 2026-11-05: its notes add nothing for this integration, all fork tests pass on it, and core's own `_entity_class_requires_readd` is False for every entity class. Coming in 2026.12: a config entry listener together with reloading methods becomes an error, and `UNDEFINED` / `UndefinedType` are deprecated for `Undefined`; the fork uses neither. 2026.11.1 (2026-11-09) was checked on 2026-11-10 the same way, with no findings.
- **Upstream issues without a device to test on**: device-specific behavior changes are not made on a report alone. Example: #1849 (`xiaomi.vacuum.pv21cn` resumes cleaning after `return_to_base`) suggests preferring `battery.start-charge` over `vacuum.stop-and-gocharge`, which would change every vacuum; it stays as upstream until there is a log or a tester.
- **"Device not created" reports**: first parse the spec with the fork's `MIoTSpecParser` and run `MIoTDevice.spec_transform()`, counting `entity_list`, `prop_list`, `event_list` and `action_list` together (properties, events and actions are not in `entity_list`). Then read the reporter's log before concluding: a `property changed` debug line from `miot_device` comes only from a property entity, so it proves entities exist for that device (look for them under another name, area or disabled state instead). Only without such lines is the device likely missing from the device cache: devices added in the app after setup, or excluded by the device filters, arrive through the device-list-changed notification and Options > Update device list; reloading or restarting does not add them (#1848). #1854 (`xiaomi.sensor_occupy.03`) converts into 7 entities and its log has `property changed` lines, so the 2026-11-08 reading "missing from the cache" was wrong; its cause is not known.
- **Spec customization data is shared and must stay unmodified**: `load_yaml_file` is cached for the whole process (fork change, May 2026), and the parser renames value-list items in place. `_SpecModify.get_prop_value_list` and `_SpecAdd.get_service_add` therefore return copies. Before that, a second parse in one process (Options > Update conversion rules, or two urns sharing an entry) took item names from translated descriptions, which changed 4 of the 8 value-list entries and breaks name-based mode mapping (for example `auto` on `qdhkl-a42`). The cache also means edits to the spec YAML files need a Home Assistant restart.
- **Spec gaps that a newer spec version fixes**: when a device reports a value its spec version does not list, check the newer versions of the same model on miot-spec.org first. If one has the value, give the old version the same list in `spec_modify.yaml`, with the same descriptions, so nothing changes when the firmware moves to the new spec. Example: `xiaomi.humidifier.600ek` and `.600` version 1 lacked mode 3 (air-dry), which version 2 has (#1855, v0.5.12).
- **Self-review**: after a series of releases, re-read the changes and the conclusions drawn from issue reports against the code and the reporters' evidence. The 2026-11-10 review found the value-list name bug fixed in v0.5.13 (the entry added in v0.5.12 ran into it) and the wrong reading of #1854. Scripts that check one case can hide state carried between parses, so vary the order and repeat the parse.
- **What Home Assistant tolerates only from custom integrations** (audit of 2026-11-11 on 2026.11.1): list every `report_usage(` call in the installed core with its `core_integration_behavior` and `custom_integration_behavior`; the ones that are ERROR for core and LOG or IGNORE for custom are the tolerated forms. The fork used one, boolean returns from the config entry methods (IGNORE, so nothing was logged), fixed in v0.5.14. Importing all modules of the integration on 2026.11.1 logs no warning. Still open: entity IDs are set explicitly, which core discourages but only reports when the ID is invalid or has the wrong domain; of 46,308 catalogue models, four give an invalid ID (two junk entries and the watch bands `xiaomi.watch.band1A` / `band1S`, uppercase in the last model segment, reported until it breaks in 2027.2). hassfest lets a custom integration leave requirements unpinned and, since 2026.11, rejects exact pins of packages Home Assistant ships, so keep them unpinned. The HACS action only warns about the missing brand icon in the repository.
- **paho callback API v2 is not adopted yet**: `_MipsClient` creates the client without `callback_api_version`, so paho 2.1.0 warns that API v1 is deprecated. Moving needs `callback_api_version=CallbackAPIVersion.VERSION2` and a five-argument `__on_disconnect` (`disconnect_flags` is added). With v2 a client-side loss no longer arrives as an `MQTT_ERR_*` integer but as a `ReasonCode` ("Unspecified error" for no connection and connection lost, "Keep alive timeout"), so the log level and auth checks of red line 11 must be rewritten with it. It can be tested with a fake MQTT v5 broker on a local socket pair that sends CONNACK and DISCONNECT packets through paho's real dispatch; what the Xiaomi cloud and the central hub gateway really send can only be confirmed on the owner's Home Assistant.
- **README**: describes the code as it is on `main` and is checked against the code when it is rewritten. Its release history lists only the current minor series (v0.5.x); older versions live in `CHANGELOG.md`. Each release adds its README entry and moves the `Latest` marker.

### Additional red lines
6. **Never build an `entity_id` from `spec.platform` alone**: entities created on a different platform (dehumidifiers, binary sensors shown as sensors, debug action text entities) must pass `ha_domain`, because HA rejects mismatched domains from 2027.5.
7. **Never use `set.union()` on spec mapping sets**: `SPEC_DEVICE_TRANS_MAP` uses `frozenset`; use the `|` operator. `MIoTSpecInstance` (whole-device entities) has no `iid` / `need_filter` / `proprietary`, so check `isinstance(..., MIoTSpecService)` before touching them.
8. **Do not override `TrackerEntity.location_name` or `battery_level`**: both are removed in HA 2027.7; battery level is a separate sensor.
9. **Never log or embed raw OAuth or profile responses**: token responses carry credentials and reach logs and diagnostics through error messages; report only the response code or the server error description.
10. **Large, frequently changing attributes stay out of the recorder**: list them in `_unrecorded_attributes` (for example the untruncated `value` of long strings).
11. **MQTT disconnect codes**: `rc` is either a paho client error code or a broker `ReasonCode` with overlapping values (4 is "no connection" as a client code). Check `isinstance(rc, ReasonCode)` before comparing values. `_MipsCloudMQTTClient` overrides paho's protected `_filter_wildcard_len_check` and `_create_socket` (the latter tries every broker address, because a node that drops the TLS handshake would otherwise keep the connection down). paho is pinned to 2.1.0 by Home Assistant; when it is bumped, re-check both overrides (`tests/test_mips_failover.py` asserts the paho internals they use).
12. **Failures the integration recovers from on its own are not errors**: log retried connection attempts and subscriptions made while offline (they are replayed on connect) at DEBUG. A lasting outage gets one WARNING that names the last error, and its recovery is logged. Keep ERROR for problems that need the user. The same goes for the user certificate: each config flow has a new random virtual did, so on a retried setup the certificate from the earlier attempt fails the COMMON_NAME check and is renewed; that is logged at INFO since v0.5.9 (#1853 showed the old ERROR misleading users).
13. **Every entity class keeps the in-place entity_id opt-in**: the four base classes in `miot/miot_device.py` define `async_entity_id_changed`, because they define `async_added_to_hass` / `async_will_remove_from_hass`. A class that defines one of those hooks (or `async_prepare_to_add_to_hass`) without the opt-in on itself or a subclass falls back to remove and re-add on rename, which HA removes in 2027.11. Subscriptions are keyed by did/siid/iid; anything new keyed by `entity_id` must be re-keyed in `async_entity_id_changed`. `tests/test_ha_compliance.py` applies core's rule to every entity class.
14. **Manifest categories must be valid values**: the HACS action fails on an unknown category. Take values from the Home Assistant category list; the integration uses `hubs_protocols.smart_home_hubs`.
15. **Writes go through `set_property_async`, and the post-command poll stays skipped**: LAN-capable entities are polled, so Home Assistant calls `async_update` right after every command. A read that soon can return the value from before the write (the cloud learns about a LAN command later), and the 1 s pending state write used to publish it, so the state flipped back for a moment (#4). `MIoTServiceEntity` and `MIoTPropertyEntity` record the time of each successful write and skip `async_update` for `_POLL_SKIP_AFTER_WRITE` (2 s). Since v0.5.11 they also ignore, for the same 2 s, every value that carries `PROP_MSG_POLLED`: the cloud, gateway and LAN refresh paths set that key on what they pass to `client.on_prop_msg`, because a refresh started elsewhere (at startup, or on an availability change) can land right after a command too. Device pushes carry no marker and always apply. A new refresh path must set the marker, and a platform that writes another way would lose the protection; `tests/test_entity_poll.py` and `tests/test_miot_managers.py` cover both. Trade-off: if a device accepts a write but does not apply it, the state is corrected by the device's push or the next regular poll (up to about 30 s), no longer by the post-command poll.

### Workflow
- Quality gate: `python3 scripts/quality_audit.py` (Chinese character policy, compilation, `tests/`, the offline `test/` suite and `test/check_rule_format.py`).
- Branch, commit, fast-forward merge into `main`, push. Contributor PRs are cherry-picked with their authorship kept, then closed with a comment.
- Releases: tag `YYYYMMDDrNN`, title `<tag> (vX.Y.Z Mod)`, notes taken from `CHANGELOG.md`. Publishing a release triggers `release.yaml`, which uploads `xiaomi_home.zip`. Claude Code may publish with `gh release create` once CI is green and the owner has agreed to the release: the owner's untracked `.claude/settings.local.json` allows that one command, because auto mode blocks it otherwise. Pass the full target SHA and a notes file, then verify the zip. Without that setting, hand the owner the complete command to run.
- New Home Assistant releases: the local `test_env` runs Home Assistant 2026.11.1 (upgraded from 2026.5.4 on 2026-11-11, when the minimum became 2026.11.0). For a newer release, create a separate venv with the same Python, `pip install homeassistant==<version> pytest pytest-asyncio pytest-dependency construct numpy psutil paho-mqtt`, and run `tests/` against it as well. Beta wheels reach PyPI later than the GitHub tags; before then, read the source at the tag (`gh api -H "Accept: application/vnd.github.raw" "repos/home-assistant/core/contents/<path>?ref=<tag>"`) and mirror the rule in a test.
- `spec_modify.yaml` keys are the cloud `spec_type` URN (with the `:0000Cxxx` suffix when the device has one). A key line ending in `:1:` is not a different URN: the last colon is YAML's key separator. `expr` runs before the sensor range check, so a scaled property gets a `value-range` in the scaled unit (see `chint1-lcd` and `sanmei-s1`).
- Repository layout: `tests/` holds this fork's unit tests (run against Home Assistant), `test/` is upstream's suite and stays as is so upstream changes cherry-pick cleanly. Finished plans and analyses from earlier work live in `docs/history/`.
- Cloud MQTT outages: the broker name `<region>-ha.mqtt.io.mi.com` (`cn`, `de`, `i2`, `ru`, `sg`, `us`) resolves to several nodes. To diagnose, resolve it and run a TLS handshake against each address on port 8883 with the broker name as SNI. In October 2026 one `sg` node (`47.236.195.180`) dropped every handshake, which led to the failover in v0.5.5.
- CI is fully green since 2026-10-24 and must stay that way: pylint reports zero findings (deliberate catch-all handlers carry an inline `# pylint: disable=broad-exception-caught`, as upstream does), and the HACS license check is skipped with `ignore: license` because `LICENSE.md` is Xiaomi's custom license without an SPDX identifier.
- If a push triggers no CI run, check `gh run list --commit <sha>` and try `gh workflow run Tests` / `gh workflow run Validate`. An HTTP 422 "Actions has been disabled for this repository" is a repository or account setting for the owner, even when the permissions API still reports Actions as enabled (this happened on 2026-11-08 and the owner re-enabled it). Do not publish a release until CI has run on its target. The workflows use `actions/checkout@v7` and `actions/setup-python@v7` (Node.js 24); GitHub forces actions built for Node.js 20 onto 24 and warns about it, so bump the major version when that warning shows up in a run log. Scheduled workflows did not resume on their own after that outage: `Upstream Release Tracker` (`upstream_tracker.yaml`, daily, cron 02:00 UTC, in practice it starts around 08:20 to 08:50 UTC) last ran on schedule on 2026-11-06. A manual `gh workflow run upstream_tracker.yaml` worked, and with the owner's go-ahead the workflow was disabled and enabled again on 2026-11-11 to register the schedule anew. When checking upstream, also check that `gh run list --workflow upstream_tracker.yaml` shows a recent `schedule` run; enabling or disabling a workflow is a repository setting and needs the owner's go-ahead.
- Fork issues: comments and closing need the owner's go-ahead. A fix that has not been checked on a real device is released with the issue left open and a comment asking for verification (#4).
